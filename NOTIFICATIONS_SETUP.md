# Smart Notifications — setup guide

StudyBun can now push up to **3 AI-written notifications a day** (morning /
afternoon / evening), each generated by reading that user's *actual* data —
tasks due today, overdue/due revisions, study minutes logged, streak,
backlog, last mock — through Groq's free-tier API. All of this runs
server-side on Vercel; no AI key ever reaches the browser.

## Architecture at a glance

```
Vercel Cron (3x/day, once each — see "Why 3 cron jobs" below)
  → /api/cron/notify?slot=morning|afternoon|evening
      → for every user with a registered device:
          - build a data snapshot (tasks/revisions/study time/streak/…)
          - ask Groq to turn it into one short, specific notification
            (multi-key rotation + auto-discovers Groq's current model
            catalog, so new models work without a code change)
          - if Groq fails for any reason, fall back to a rule-based
            notification so the user never gets nothing
          - send it via Web Push to every device the user has registered
          - log it (dedup guard: never 2 sends of the same slot/day)

Browser: Settings → Smart Notifications
  → requests permission, creates a Web Push subscription,
    registers it at /api/push/subscribe
  → custom service worker (src/sw.js) shows the system notification
    and deep-links a tap straight to the relevant page in the app
```

## 1. Run the database migration

In the Supabase SQL editor, run:

```
supabase/migration_smart_notifications.sql
```

This adds `push_subscriptions`, `notification_prefs`, and
`notification_log` (all RLS-protected — see the file for details). Safe to
run on an existing database.

## 2. Generate a VAPID key pair (Web Push identity)

```bash
npx web-push generate-vapid-keys
```

This prints a public and private key. The **public** key is safe to expose
to the browser (that's how Web Push works). The **private** key must never
leave the server.

## 3. Get Groq API keys (free tier)

Create one or more free keys at [console.groq.com/keys](https://console.groq.com/keys).
Using more than one key isn't required, but it multiplies your effective
free-tier rate limit — recommended if you have more than a handful of users,
since each key gets its own daily/per-minute quota and the server
automatically rotates across all of them.

## 4. Set environment variables in Vercel

Project → Settings → Environment Variables. **Server-side vars must NOT have
a `VITE_` prefix** — that prefix tells Vite to inline the value into the
browser bundle, which is exactly what we don't want for these.

| Variable | Where it's used | Notes |
|---|---|---|
| `SUPABASE_URL` | server | same value as `VITE_SUPABASE_URL` |
| `SUPABASE_SERVICE_ROLE_KEY` | server | Supabase → Settings → API → `service_role` key. **Never** prefix with `VITE_`. |
| `GROQ_API_KEYS` | server | comma-separated list, e.g. `gsk_aaa,gsk_bbb,gsk_ccc` |
| `GROQ_API_KEY` | server | fallback if you only have one key |
| `GROQ_MODEL` | server, optional | pin a specific model id first in the try-order; otherwise it's auto-discovered from Groq's live catalog |
| `VAPID_PUBLIC_KEY` | server | from step 2 |
| `VAPID_PRIVATE_KEY` | server | from step 2 — **secret** |
| `VAPID_SUBJECT` | server, optional | `mailto:you@yourdomain.com`, defaults to a placeholder |
| `VITE_VAPID_PUBLIC_KEY` | client (Vite-inlined) | **same value** as `VAPID_PUBLIC_KEY` above — the browser needs the public half to create a subscription |
| `CRON_SECRET` | server | Vercel auto-populates this once you add it as an env var and sends it as `Authorization: Bearer $CRON_SECRET` on real cron invocations, so `/api/cron/notify` can reject anyone else hitting the URL. Set any random string. |

You already have `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` configured
for the rest of the app — those are unrelated to and unaffected by this.

## 5. Deploy

`vercel.json` (already added) registers three cron jobs:

```json
{ "path": "/api/cron/notify?slot=morning",   "schedule": "0 3 * * *"  },  // 08:30 IST
{ "path": "/api/cron/notify?slot=afternoon", "schedule": "0 9 * * *"  },  // 14:30 IST
{ "path": "/api/cron/notify?slot=evening",   "schedule": "30 14 * * *" } // 20:00 IST
```

### Why three separate cron jobs, not one that fires 3x/day?

Vercel's **Hobby (free) plan only allows a cron *expression* that fires
once per day** — anything more frequent fails at deploy time. It does,
however, allow up to 100 separate cron job *entries* per project. So instead
of one job running 3 times a day, this uses **three independent jobs**, each
firing once a day at a different fixed UTC time — which adds up to exactly
the 3x/day behavior you asked for, entirely on the free tier. Two caveats
worth knowing:
- Vercel schedules are UTC-only, and on Hobby the exact trigger time can
  drift up to an hour from what's scheduled (e.g. `0 3 * * *` fires
  sometime between 03:00–03:59 UTC) — fine for a "your day's notification"
  use case, not fine if you need second-precision.
- If you upgrade to Pro later, you get per-minute precision and could
  collapse this to fewer jobs if you ever wanted a more dynamic schedule.

## 6. Try it

1. Deploy, sign in, go to **Settings → Smart Notifications**.
2. Click **Enable notifications**, accept the browser permission prompt.
3. Click **Send test notification** — this calls `/api/push/test`
   immediately (no need to wait for a cron tick) and exercises the exact
   same Groq pipeline the real 3x/day sends use.
4. To verify the real cron path without waiting for the schedule, you can
   manually call (while signed in as yourself isn't required — this is a
   server-to-server route protected by `CRON_SECRET`):
   `https://your-app.vercel.app/api/cron/notify?slot=morning&secret=YOUR_CRON_SECRET`

## Notes on the AI layer

- **Multi-key rotation**: round-robins across every key in `GROQ_API_KEYS`
  that isn't currently rate-limited/invalid; a 429 cools a key down for 60s,
  a 401/403 marks it invalid for the life of that server instance.
- **"All new models" compatibility**: rather than hard-coding a model name
  (which breaks the moment Groq renames or retires it — this happens often;
  see `console.groq.com/docs/deprecations`), the server fetches Groq's live
  `GET /openai/v1/models` catalog, filters out non-chat models (audio/TTS/
  moderation), and tries them in a preference order. Anything Groq adds in
  the future is picked up automatically on the next cache refresh (6h TTL) —
  no redeploy needed. A hard-coded list is kept only as an emergency
  fallback if the catalog fetch itself fails.
- **Never silent-fails**: if every key/model combination fails for a given
  user, a rule-based fallback notification is generated instead (still
  grounded in their real data — "2 revisions overdue", etc.) so a Groq
  outage never means users get nothing.
- **Per-user, per-slot preferences** live in `notification_prefs` and are
  editable straight from Settings (RLS-protected, no extra API route
  needed) — users can turn off just the afternoon nudge, for instance.
